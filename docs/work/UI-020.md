# UI-020 — Compact dashboard single height owner

## Status
VERIFIED ON PR — PR #226 passed all eight established workflows on head `c9c9a212e4177e6463af9cd00989e3e01fff7c18`; awaiting final documentation-head CI and merge to `main`.

## Goal
Keep the vertical space reclaimed by the compact Commands-menu layout stable across resize, expand/collapse and DPI changes so Live Activity remains visible.

## Root cause
`CompactTopCommandMenuExperience` requested compact Development Plan / Runtime Health heights while `ExpandableWorkspaceLayout` independently reapplied the legacy heights on `SizeChanged` and `DpiChangedAfterParent`. The two height owners could therefore fight and restore vertical chrome after the compact UI had already removed it.

## Implementation
- `ExpandableWorkspaceLayout` is now the single physical-height owner for expandable workspaces.
- Added explicit compact-operator registration for Development Plan and Runtime Health.
- Compact mode uses logical heights 58/118 for Development Plan and 58/140 for Runtime Health.
- Non-compact controls retain their existing 72/178 and 62/188 logical heights.
- `CompactTopCommandMenuExperience` only enables compact mode; it no longer owns height constants or expanded-state height event handlers.
- Details remain available from the Commands menu.
- Regression tests verify single ownership, compact values, resize/DPI reapplication and legacy fallback values.

## Safety invariants
- No monitor/runtime command behavior changes.
- Existing control expanded/collapsed state remains authoritative.
- History workspace heights are unchanged.
- Compact mode is opt-in and only activated by the compact command-menu experience.
