# MON-015 — Persistent fresh-chat handoff continuity

## Status
IMPLEMENTED / RUNTIME REGRESSION GREEN / PR FULL VALIDATION RUNNING

## Problem
Long-running monitors can hit an explicit ChatGPT delivery timeout or another rendered error, create a fresh ChatGPT chat, and then lose the exact continuation point. Field diagnostics showed the first fresh-chat delivery could still be observed under the source conversation scope before the new stable conversation identity was committed. A process/CDP interruption inside that window could leave the new chat accepted but the monitor still persisted against the old conversation.

## Required behavior
1. Persist the latest confirmed work checkpoint before a fresh-chat handoff starts.
2. Build the continuation packet from recent confirmed inbound/outbound state instead of sending a bare `كمل` for timeout/error recovery.
3. Persist handoff transaction stages across process restarts: `Prepared -> TargetCreated -> DeliveryAccepted -> TargetResolved`.
4. Attribute the fresh-chat physical send to the new Chrome target scope.
5. Never blindly resend an accepted continuation when stable conversation identity or SQLite commit is temporarily unavailable.
6. Reconcile an accepted pending handoff before startup sends any normal follow-up.
7. Keep initial CDP recovery alive until explicit cancellation instead of terminating the monitor after three transient startup failures.

## Implementation
- Added `ConversationHandoffCheckpointStore` backed by `AppSettings` key `Runtime.PendingConversationHandoff.{MonitorId}`. This avoids a schema migration while making the handoff durable across application restarts.
- Expanded `ConversationHandoffService` to carry an explicit confirmed checkpoint, latest confirmed outbound instruction, trigger state, and bounded recent history for all fresh-chat recovery paths.
- The configured recovery/start directive remains the literal prefix of the fresh-chat message, followed by a canonical one-line `[HANDOFF-CHECKPOINT]` payload so existing exactly-once rendered-message verification remains deterministic.
- Updated delivery-timeout, generic-error, context-limit, and assistant-count rotation flows in `ChatGptMonitorService` to persist and reconcile the handoff stages.
- Added a nested `RuntimeFlightRecorder` scope for the fresh target so diagnostics no longer inherit the old conversation scope during the first continuation send.
- Accepted-but-uncommitted handoffs keep the source response handled and are reconciled from the persisted checkpoint without opening another fresh chat or sending another continuation.
- Updated `LastWorkingStateService` to finish an accepted pending handoff before normal saved-tab recovery and suppress the duplicate startup follow-up for that recovery cycle.
- Changed initial CDP state acquisition to cancellation-bound self-healing retry with capped backoff instead of stopping after three transient failures.
- Preserved the existing source-level `DeliveryTimeout` recovery contract with explicit named handoff arguments so the existing regression suite continues to guard the behavior.

## Verification
- `HandoffContinuityCheckpointRegressionTests` covers timeout handoff scope, no re-arm after accepted commit deferral, explicit continuation checkpoint content, configured-directive preservation, startup reconciliation ordering, indefinite initial CDP self-healing, and SQLite persistence across reopening the database.
- One-shot integration actions applied the source changes and completed the runtime regression suite successfully before committing the integrated source.
- Repository-wide PR validation is being rerun from a user-authored commit so GitHub evaluates all normal Build/QA gates against the final integrated code.
