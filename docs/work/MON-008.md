# MON-008 — Monitor Start/Stop Lifecycle Serialization

Issue: #107

Implementation branch: `agent/mon-008-monitor-lifecycle-serialization`

Status: **IN PROGRESS**

## Objective

Prevent a rapid or concurrent Start from creating a replacement worker for the same Monitor ID while the previous worker is still completing Stop/cancellation.

## Root cause

`StopMonitorAsync` previously removed the runtime from `_running` before cancelling and awaiting the worker. That made the Monitor ID appear restartable before shutdown was actually complete. A new Start could therefore create a replacement worker while the old worker was still unwinding cancellation/finalization.

## Implementation contract

1. Start and Stop use the same keyed lifecycle gate for a given Monitor ID.
2. Different Monitor IDs use different gates so independent monitors do not block one another.
3. Stop reads the existing runtime without removing it first.
4. Stop cancels and awaits the existing worker before the explicit final runtime removal.
5. Final removal is identity-guarded so an old lifecycle can never remove a newer runtime instance.
6. Natural/fatal worker completion keeps the existing token-identity self-removal guard.
7. Existing duplicate-ownership, conversation identity, recovery, rotation and delivery behavior is unchanged.

## Regression coverage

`ChatMonitorLifecycleSerializationTests.cs` locks:

- keyed lifecycle-gate usage in Start and Stop;
- no early `_running.Remove(..., out runtime)` in Stop;
- worker-await ordering before final removal;
- runtime identity guard with `ReferenceEquals`;
- absence of a global lifecycle semaphore that would serialize unrelated monitors.
