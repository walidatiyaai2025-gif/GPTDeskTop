## Objective

Prevent a saved monitor from being deleted while a stale Start creates or preserves a runtime worker for the same Monitor ID.

## Root cause

The operator delete path previously performed `StopMonitorAsync(id)` and `LocalDatabase.DeleteMonitorAsync(id)` as two independent awaited operations. A Start or Start All event could interleave after Stop released the per-monitor lifecycle gate but before the persisted row was deleted.

`ChatGptMonitorService.StartMonitorAsync` also did not require the supplied Monitor ID and conversation identity to still match a current SQLite row immediately before worker creation. A stale caller could therefore create an orphan runtime after deletion.

## Implemented contract

1. Start, Stop and Delete use the same keyed lifecycle gate for a Monitor ID.
2. Delete holds that gate across both worker shutdown and persisted monitor deletion.
3. Stop logic is shared through a private `StopMonitorCoreAsync` so Delete does not re-enter the same semaphore.
4. Start reloads saved monitors after acquiring the lifecycle gate.
5. Start refuses a missing Monitor ID before `_running.Add`.
6. Start refuses a stale persisted conversation identity before `_running.Add`.
7. MainForm delegates monitor deletion to one service-level serialized operation instead of separate Stop and database Delete calls.
8. MON-009 cleanup ownership and runtime identity guards remain intact.

## Regression coverage

`MonitorDeletionLifecycleTests.cs` covers:

- direct Start of a deleted Monitor ID is ignored before worker creation;
- direct Start of a stale conversation binding is ignored before worker creation;
- serialized Delete removes a stopped persisted monitor;
- source-contract ordering for Start/Stop/Delete and the shared lifecycle gate;
- MainForm uses the single serialized deletion boundary;
- MON-009 cleanup ownership remains present in the shared Stop core.
