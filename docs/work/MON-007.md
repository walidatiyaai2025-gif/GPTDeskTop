## Objective

Make the monitor passive while ChatGPT is legitimately working. Response duration, unchanged text, temporary empty output, thinking, reasoning, or streaming are not failures and must never cause a page refresh or recovery by themselves.

## Runtime contract

1. `IsGenerating == true` is an indefinite wait state unless an explicit current error is present.
2. Empty or unchanged assistant output is an indefinite wait state.
3. Elapsed time alone cannot call `ReloadTabAsync`, create a new chat, rotate a conversation, or send a recovery message.
4. Explicit current ChatGPT error UI still follows the normal error path.
5. Explicit `message delivery timed out` still uses the verified new-chat recovery path.
6. Explicit conversation/context-limit text still uses the verified conversation handoff path.
7. Transient CDP failures remain background retry conditions and do not become page errors.
8. Error UI detection is scoped to visible structured error/retry elements. Historical conversation body text is not scanned for error phrases.
9. Generic error recovery requires current structured `ErrorText`; normal assistant prose containing an error phrase is not itself a recovery trigger.

## Implementation

- Removed the `NoResponseRefreshSeconds` read and elapsed-time reload branch from `ChatGptMonitorService`.
- Removed `lastResponseActivity` bookkeeping from the monitor worker.
- Added explicit runtime activity text declaring passive long-response wait mode.
- Kept existing explicit error, delivery-timeout, context-limit, message-count rotation, and transient-CDP behavior.
- Hardened `ChromeDevToolsService.GetChatStateAsync` with visible-element filtering, visible stop-button detection, streaming signals, and structured current error elements only.
- Removed the whole-page `document.body.innerText` error fallback to prevent historical error phrases from being treated as current failures.
- Removed generic assistant-text error phrase classification from the recovery decision; generic recovery now requires current structured error UI.

## Regression coverage

- `ChatMonitorErrorDrivenWaitRegressionTests.cs` locks the source/runtime policy.
- The legacy `--qa-no-response-probe` command is retained for CI compatibility but now validates watchdog retirement.
- Real Chrome QA deliberately keeps `NoResponseRefreshSeconds=30`, runs a generating response for 40 seconds on load 1, and requires zero elapsed-time refreshes.
- The same probe includes historical `Something went wrong` conversation text and requires no false error refresh.
- A second tab surfaces a visible current `role=alert` error after 35 seconds and must be refreshed exactly once to load 2.

## Compatibility

`NoResponseRefreshSeconds` remains in persistence/settings/backup compatibility for now, but it is not consumed by the production monitor loop. Removing or relabeling that legacy operator field can be handled as a separate settings migration without coupling it to this runtime-safety fix.
