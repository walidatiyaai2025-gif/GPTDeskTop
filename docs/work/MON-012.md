# MON-012 — Fresh Persisted Start Configuration / Serialized Settings Save

Issue: #133

Implementation branch: `agent/mon-012-persisted-start-config`

Status: **IN PROGRESS — implementation and regression coverage complete; CI verification pending**

## Objective

Ensure every newly-started monitor worker uses the latest persisted monitor configuration from SQLite, and serialize operator settings saves with Start/Stop/Delete for the same Monitor ID.

## Root cause

`ChatGptMonitorService.StartMonitorAsync` already reloaded the saved monitor row under the per-monitor lifecycle gate for existence and conversation-identity checks, but it still created `MonitorLoopAsync` with the caller-supplied `SavedMonitor` object. A stale caller snapshot could therefore supply outdated AutoReply, poll timer, reply delay, rotation, RotationCount or model-routing values to a new worker even though SQLite contained newer settings.

`MainForm.EditSelectedMonitorSettingsAsync` also persisted changes directly through `LocalDatabase.UpdateMonitorConfigurationAsync` outside the monitor lifecycle gate. A concurrent Start could therefore win after the UI's initial `IsMonitorRunning` check but before the settings save completed.

## Implementation contract

1. The incoming Start monitor object provides requested Monitor ID/conversation identity only; it is not the authoritative runtime configuration.
2. After acquiring the per-monitor lifecycle lease, Start reloads the current SQLite row.
3. The fresh persisted row is validated for conversation identity and non-empty AutoReply.
4. Duplicate-owner diagnostics use the fresh persisted identity/title.
5. Worker creation calls `MonitorLoopAsync(persistedMonitor, ...)` and registers the persisted Monitor ID.
6. `ChatGptMonitorService.UpdateMonitorConfigurationAsync` acquires the same per-monitor lifecycle lease used by Start/Stop/Delete.
7. A settings save returns `false` without database mutation if the Monitor ID is already running when the save acquires the gate.
8. If the save wins the gate first, it commits configuration-only fields and a queued Start subsequently reloads those persisted values.
9. MainForm routes existing-monitor settings persistence through the monitor service instead of calling the database directly.
10. If a settings save loses to Start, MainForm refreshes from SQLite so unsaved dialog values cannot remain presented as persisted state.
11. The existing database configuration update remains identity-safe: it does not write TabId, Title, Url or RotationCount.

## Regression coverage

`MonitorPersistedStartConfigurationTests.cs` adds real-SQLite and source-contract coverage for:

- stale caller Start with empty/old AutoReply, timer, delay and title still starts from the fresh persisted configuration;
- an already-running monitor rejects a queued settings save without mutating SQLite;
- a settings save that completes before Start is reloaded and used by the subsequent worker;
- Start explicitly creates the worker from `persistedMonitor`, not the caller snapshot;
- settings update uses the same lifecycle gate and refuses a running monitor;
- MainForm uses the service boundary and refreshes after a lost save race.

`MonitorConfigurationUpdateTests.cs` retains all existing handoff/repair identity-safety coverage and now asserts that the UI reaches the config-only database update through the serialized service boundary.

## Compatibility

No live hot-reload is added to already-running workers. No ChatGPT DOM/CDP behavior, passive long-response waiting, delivery verification, conversation rotation algorithm, recovery algorithm, SQLite schema, configuration import/export, Setup packaging or stable-release publisher behavior is intentionally changed.
