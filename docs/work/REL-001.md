# REL-001 — Root Last release Stable EXE

Issue: #95

Implementation branch: `agent/rel-001-last-release`

Status: **IN PROGRESS**

## Objective

Keep a root-level `Last release` folder that always points operators to the newest verified stable Windows x64 GPTDeskTop application executable.

## Stable publication contract

1. The primary file is `Last release/GPTDeskTop.exe`.
2. The executable is published as Release / win-x64 / self-contained / single-file.
3. Publication is allowed only for a `main` source commit.
4. The same source SHA must pass all eight required stable workflows before publication.
5. `RELEASE.txt` records source SHA, file version, generation time, 8/8 validation and SHA-256.
6. Publication aborts if `main` advances while the executable is being prepared.
7. The generated release-only commit uses `[skip ci]` so it cannot recursively trigger another publication cycle.
8. The publisher refuses an executable near GitHub's 100 MB per-file limit instead of creating an invalid repository commit.

## Required stable workflows

- Build GPTDeskTop
- QA Release x64
- QA Hidden Chrome CDP
- QA Crash Process Recovery
- QA Passive Chat Wait
- Development Delivery Receipts
- Development Task Recovery
- Development Message Reload

## Initial delivery

After the workflow implementation is merged to `main`, the resulting main source commit must pass the complete gate set. The workflow then builds and commits the first `Last release/GPTDeskTop.exe` plus its release receipt.

## Regression coverage

`LastReleasePublisherRegressionTests.cs` locks the gate list, same-SHA requirement, x64 single-file publication, `Last release` path, SHA-256 receipt, stale-main guard and recursion guard.
