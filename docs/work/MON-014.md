# MON-014 — Treat offline Chrome DevTools probes as availability state

- **Status:** Implemented
- **Priority:** High
- **Area:** Browser integration / diagnostics
- **Target branch:** `main`

## Problem

When the dedicated monitor Chrome process is not listening on the configured Chrome DevTools endpoint (normally `127.0.0.1:9222`), the read-only Runtime Health and Support Bundle probes receive `SocketError.ConnectionRefused` through `HttpRequestException`.

Both probes already convert that condition into an unavailable Chrome health snapshot, but they also sent the exception to `ExceptionLogService`. This produced repeated crash-style diagnostics even though an operator-controlled Chrome instance simply being offline is an expected availability state.

## Root cause

`ChromeDevToolsService.GetTabsAsync()` correctly reports an unreachable CDP endpoint by throwing. The probe boundaries correctly translate the failure into `ChromeReachable = false`, but the generic catch blocks log every exception before returning that availability result.

Auto-launching Chrome from these probes is intentionally avoided: Runtime Health and Support Bundle are read-only diagnostics, while Chrome lifecycle remains explicitly operator-controlled.

## Implementation

- Added a narrow classifier in `ExceptionLogService` for the two read-only Chrome probe sources:
  - `RuntimeHealthControl.ChromeProbe`
  - `SupportBundle.ChromeProbe`
- Suppress persistence/event emission only when the exception chain contains `SocketException` with `SocketError.ConnectionRefused`.
- Preserve the existing unavailable health/support result so the UI still reports Chrome as unavailable until Monitor Chrome is launched.
- Continue logging every other Chrome failure, including other socket errors, HTTP/protocol failures, and all monitor/runtime failures.

## Regression coverage

`ChromeProbeLoggingRegressionTests` verifies:

1. Connection-refused is treated as expected for both read-only Chrome probes.
2. The same connection-refused error outside those probes remains diagnostic.
3. Other socket failures remain diagnostic.
4. Other HTTP/CDP failures remain diagnostic.

## Acceptance criteria

- No new persistent exception entry is created solely because port 9222 has no listener during Runtime Health or Support Bundle collection.
- Runtime Health still displays Chrome as unavailable while CDP is offline.
- Support Bundle still records Chrome as unreachable while CDP is offline.
- Unexpected Chrome and monitor failures remain visible in the existing exception diagnostics.
