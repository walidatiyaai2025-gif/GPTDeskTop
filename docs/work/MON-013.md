# MON-013 — Live Chrome Target Revalidation Inside Start Boundary

Issue: #136

Implementation branch: `agent/mon-013-live-target-revalidation`

Status: **IN PROGRESS — implementation and regression coverage complete; CI verification pending**

## Objective

Prevent a queued Start from creating a worker against a Chrome target whose live conversation identity changed or disappeared after the caller's pre-gate tab snapshot was captured.

## Root cause

`StartMonitorAsync` validated `monitor.Url` against the caller-supplied `ChromeTab.Url` before waiting for the per-monitor lifecycle gate. The `ChromeTab` came from an earlier Chrome `/json/list` snapshot. A target can navigate or disappear while Start waits, while later CDP commands still use that target/WebSocket. The pre-gate URL check therefore could become stale before worker creation.

MainForm also persisted runtime target ID/title directly before entering the monitor-service Start boundary, leaving runtime target metadata mutation outside the lifecycle serialization used for Start/Stop/Delete/settings.

## Implementation contract

1. Start retains the fast pre-gate caller identity validation.
2. After acquiring the lifecycle lease and reloading the persisted monitor row, Start calls Chrome `/json/list` again.
3. The requested target is resolved by exact Target ID from the fresh list.
4. Start is rejected before `_running.Add` if the target disappeared.
5. Start is rejected if the fresh target is no longer a stable ChatGPT conversation URL.
6. Start is rejected if the fresh target conversation identity differs from the persisted monitor identity.
7. Runtime target ID/title persistence is performed inside the service Start lifecycle boundary using the expected persisted conversation URL guard.
8. The persisted monitor snapshot is updated only with the fresh target ID/title after that guarded database update succeeds.
9. Worker creation uses `MonitorLoopAsync(persistedMonitor, liveTab, ...)`, including the fresh WebSocket debugger URL and title.
10. MainForm only resolves the intended open tab and delegates Start; it no longer writes runtime target metadata directly.
11. MON-012 fresh persisted configuration semantics remain unchanged.

## Regression coverage

`MonitorLiveTargetRevalidationTests.cs` provides deterministic real-SQLite + fake Chrome-list coverage for:

- a target that navigates to another conversation before Start is rejected and cannot alter saved target metadata;
- a target that disappears before Start is rejected;
- a fresh same-conversation target commits its current target/title metadata;
- source ordering requires fresh Chrome-list read and live identity validation after the lifecycle lease/persisted row and before target commit/worker creation;
- the worker explicitly receives `liveTab`;
- MainForm no longer performs the runtime target database update.

`MonitorPersistedStartConfigurationTests.cs` now uses a deterministic Chrome-list HTTP handler so MON-012 fresh-configuration tests exercise the new live-target boundary without depending on a local Chrome instance.

`OperatorStartConversationIdentityTests.cs` is updated to keep its original identity-safety guarantees while asserting service-owned runtime target persistence.

## Compatibility

No automatic navigation or rebinding is introduced. No DOM selector, passive long-response waiting, delivery verification, recovery algorithm, rotation algorithm, SQLite schema, configuration import/export, Setup or stable-release publisher behavior is intentionally changed.
